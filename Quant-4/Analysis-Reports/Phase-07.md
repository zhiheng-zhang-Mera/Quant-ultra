# Phase_7_FSM_Backtest：状态机回测深度解析

## 概述

Phase_7（FSM Backtest）是 Quant‑4 系统的**高仿真事件驱动回测层**，负责将 Phase_6 产出的理论权重向量（`daily_weights`）转化为逐日模拟交易记录与净值曲线。该阶段的核心使命是：拒绝理想化的“假设成交”，通过有限状态机（FSM）严格模拟订单生命周期（提交→部分成交→完全成交/取消），并融入停牌/退市处理、整手截断、平方根市场冲击、交易税费、停牌减值以及账本强制对账等真实市场微观结构特征。

Phase_7 严格遵循 Quant‑4 系统手册中“阶段七”的要求，实现了毫秒/分钟级高仿真回测。其设计将学术严谨性（如点时间 PIT 价格对齐、停牌穿透）与工程防御性（如账户借贷必相等断言、时区熔断自愈）融为一体，是验证策略实盘可行性的最后一道物理防火墙。

---

## 模块总览与协作关系

| 文件 | 核心职责 | 依赖关系 |
|------|----------|----------|
| `__init__.py` | 暴露 `execute` 入口 | 被 `main_engine.py` 调用 |
| `config.py` | 定义交易费率、滑点、停牌减值、整手单元、冲击参数、初始资金 | 被所有子模块引用 |
| `market_utils.py` | 提供 PIT 价格查询、停牌穿透回溯、前收盘价提取 | 被 `FSMEngine` 和 `execution_fsm` 引用 |
| `risk_guard.py` | 基于 ADV20 和账户 NAV 计算个股流动性持仓上限 | 被 `FSMEngine` 在日循环中调用 |
| `execution_fsm.py` | 实现 FSM 核心状态机：执行撮合（State 4）、权益处理（State 5）、账目核对（State 6） | 依赖 `market_utils` 和 `config` |
| `step7_fsm_backtest.py` | 主控引擎类 `FSMEngine`，负责日循环调度、权重风控过滤、结果封装 | 聚合所有子模块 |

## 各模块详解

### 1. `config.py` —— 回测参数与费率清单

**功能**  
定义 Phase_7 运行所需的全量交易参数：
- **税费结构**：经手费（`0.0000487`）、过户费（`0.00002`）、印花税（`0.0005`，仅卖出）
- **滑点与冲击**：基础滑点 `2bp`、平方根冲击基准系数（`STATIC_KAPPA_IMPACT=0.001`）与弹性系数（`STATIC_ALPHA_IMPACT=0.5`）
- **停牌与退市**：触发减值的持续停牌天数阈值（20天）、减值率（10%）、退市残值率（0%）
- **风控约束**：隔夜高开追高防御阈值（7%）、单票绝对持仓上限（10%）
- **交易规则**：科创板整手（200股）、主板/创业板整手（100股）
- **初始资金**：1000万人民币

**设计亮点**  
- 费率设定参照 A 股真实交易成本，提升了回测的财务真实性。
- 停牌与退市参数的引入体现了对极端流动性事件的敬畏。

**客观缺陷**  
- **冲击参数未启用**：`STATIC_KAPPA_IMPACT` 和 `STATIC_ALPHA_IMPACT` 虽在 `config.py` 中定义，但在 `execution_fsm.py` 的 `process_state_4_execution` 中，冲击计算被硬编码为 `0.001 * (turnover ** 0.5)`，完全绕过了配置系统，导致调参失效。
- 所有参数均为固定值，未支持从外部 YAML 动态覆写，与主框架的配置管理机制脱节。

---

### 2. `market_utils.py` —— PIT 价格对齐与停牌穿透

**功能**  
- **`get_prices_for_date`**：对给定日期和资产列表，从 `data_bus` 查询 `total_return_price`。若当日价格缺失（停牌），则向后回溯最多 `lookback_days`（默认 10 天）寻找最近的有效价格，返回 `None` 表示完全无法定价。
- **`get_previous_close_price`**：提取前一有效交易日的收盘价，用于计算隔夜跳空缺口（`gap`），支撑追高防御逻辑。

**设计哲学**  
- “停牌穿透”机制确保了回测中持有停牌资产时能获得一个参考估值（而非报错），使净值曲线保持连续性。
- PIT 查询严格遵循 `data_bus.query_by_pit`，杜绝未来函数。

**优点**  
- 价格缓存（`price_cache`）避免了在同一交易日内对同一资产价格的重复查询，减少 I/O 开销。
- 回溯天数可配置，应对长假等特殊场景。

**客观缺陷**  
- 穿透价格使用前向填充（向前回溯），而非按停牌天数进行减值调整（减值逻辑在 `execution_fsm` 中独立处理，二者存在功能重叠但未统一，可能导致估值不一致）。
- 若某资产停牌超过 `lookback_days`（10 天），`get_prices_for_date` 返回 `None`，但在 `execution_fsm` 中会触发 `halt_counter` 累积，两者对停牌的判定标准不同步，可能产生逻辑冲突。

---

### 3. `risk_guard.py` —— 微观流动性个体容量哨兵

**功能**  
- **`compute_individual_position_limit`**：计算单只个股在账户中的最大允许权重：
  - 优先查询 `adv_20`（20 日平均成交额），若缺失则降级为 `adv`。
  - 计算流动性容量上限：`liq_cap = (ADV_20 * 10%) / NAV`。
  - 将结果截断至 `[1%, 10%]` 区间，作为该标的的权重硬上限。

**设计意图**  
实现系统手册中“单票最大权重 = min(10%, 10% * ADV_20 / 账户可用总权益)”的审慎容量管理，防止策略在流动性枯竭的小市值股票上过度集中。

**客观缺陷**  
- 依赖 `data_bus.query_by_pit` 查询 `"adv_20"`，但 Phase_1/3 的数据管道中并未明确写入该字段（Phase_1 存储了 `adv`，Phase_3 预计算了 `adv_ma20` 但未通过 `append_atom` 持久化到 PIT 总线），导致该查询大概率返回 `None`，进而降级至 `adv` 或兜底值 `2e7`，使流动性约束形同虚设。
- 权重上限与凸优化器中的 `_compute_individual_shares_upper` 功能高度重叠，但计算逻辑存在细微差异（前者除以 NAV，后者乘以 10% 后除以 NAV），可能导致前后不一致。

---

### 4. `execution_fsm.py` —— 订单状态机核心

**功能**  
该模块实现了三个关键状态（State 4~6）：

- **State 4：撮合执行**：
  1. 退市资产强制清算（按残值率卖出）。
  2. 停牌状态更新与减值计提：若连续停牌超过阈值（20 天），一次性对持仓施加 `impairment_factor = 0.9`（减值 10%）。
  3. 先卖后买：遍历资产，计算目标值与当前持仓的差额，若需卖出则执行整手截断并卖出。
  4. 买入执行：计算可买股数（整手），引入平方根市场冲击 `impact = 0.001 * sqrt(turnover)`，调整执行价格，扣除税费后完成买入。
- **State 5：权益/分红处理**：当前为占位接口（`pass`），预留未来扩展。
- **State 6：账目核对**：强制对账，计算 `现金 + 持仓市值` 与 `calc_nav()` 的差额，若偏差 > 1 元则抛出 `RuntimeError` 熔断流水线。

**设计哲学**  
- 强制“先卖后买”顺序，防止日内资金透支。
- 整手截断（`np.floor(shares / lot) * lot`）严格复现实盘交易规则。
- 平方根冲击模型符合学术界对市场冲击的共识（冲击与交易量占比的平方根成正比）。

**优点**  
- 账目核对是回测诚信的压舱石，任何会计错误都会立即暴露。
- 停牌减值采用“一次性计提”而非每日摊销，符合会计准则的谨慎性原则。
- 退市残值率可配置，支持不同市场规则。

**客观缺陷**  
- **冲击系数硬编码**：`impact = 0.001 * (turnover ** 0.5)` 中的 `0.001` 和 `0.5` 写死在代码中，未引用 `config` 中的 `STATIC_KAPPA_IMPACT` 和 `STATIC_ALPHA_IMPACT`。
- **缺乏订单状态枚举**：虽名为 FSM，但并未显式定义 `PENDING`、`SUBMITTED`、`PARTIAL_FILLED` 等状态类，而是通过顺序函数调用隐式模拟，降低了状态机的可维护性和扩展性。
- **滑点双重计算**：`process_state_4_execution` 买入时使用了冲击调整价格 `exec_price = price * (1.0 + impact)`，但未叠加 `config` 中的 `slippage_bps` 基础滑点，可能导致滑点低估。
- **卖出冲击方向正确**：卖出时 `exec_price = price * (1.0 - impact)`，符合大额卖出压低成交价的直觉。

### 5. `step7_fsm_backtest.py` —— FSM 主控引擎

**功能**  
- **`FSMEngine` 类**：
  - **初始化**：从 `context` 提取 `daily_weights`（权重矩阵），处理时区对齐和列名适配（尤其是 MultiIndex 列，用于解析共形预测区间 `q_low`/`q_high`）。
  - **`run_engine_pipeline`**：对测试集日期进行循环：
    1. **价格获取**：通过 `get_prices_for_date` 获取当日全资产价格。
    2. **权重风控过滤**：
       - 追高防御：若隔夜涨幅 ≥ 7%，强制将该资产权重置为 0。
       - 单票限额：调用 `compute_individual_position_limit` 截断超限权重。
       - 重归一化：若总权重 > 1，等比例压缩至 1。
    3. **执行状态机**：依次调用 `process_state_4_execution`、`process_state_5_equity`、`process_state_6_reconciliation`。
    4. **净值与收益记录**：计算当日收盘净值及收益率。
    5. **共形违规检测**：利用 `q_low`/`q_high` 面板，计算组合加权预测区间，判断实际收益是否落在区间内，记录违规次数。
  - **辅助方法**：`calc_nav`（考虑减值）、`_check_is_delisted`、`_sell_asset_action`（封装卖出冲击和税费）。
- **`execute` 入口**：实例化 `FSMEngine` 并运行，将结果（`daily_nav`、`daily_returns`、`violations`）写回 `pipeline_context`。

**设计亮点**  
- **自适应截面维度对齐引擎**：代码中包含一套完整的 `daily_intervals` 列名嗅探逻辑，支持单层索引和 MultiIndex，能自动识别 `q_low`/`q_high` 的列名变体（如 `q_lower`、`lower`、`q_0.025` 等），极大增强了与 Phase_6 输出的兼容性。
- **时区自适应动态锚定**：主动提取 `data_bus._tz`，将 `daily_weights` 和 `daily_intervals` 的索引统一时区，彻底消灭了 `tz-naive` 与 `tz-aware` 的熔断冲突。
- **强对账机制**：每笔交易后执行会计恒等式校验，一旦偏差 > 1 元立即硬熔断，防止“纸面富贵”累积为系统性错误。

**客观缺陷**  
- **共形检测形同虚设**：Phase_6 的 `daily_intervals` 被硬编码为全 `0.02` 的常量 DataFrame，因此违规检测 `port_low <= ret <= port_high` 实际上是在判断收益是否在 `±2%` 内，与真正的共形预测毫无关系。这导致 Phase_7 努力构建的复杂区间解析逻辑完全浪费。
- **调试代码陷阱**：虽然本模块未显式包含 `test_dates[-3:]` 的剪裁（该逻辑在 Phase_6 中），但 Phase_6 的剪裁已严重缩短了回测周期，Phase_7 直接继承该缩减后的日期列表，用户需警惕。
- **单票限额与凸优化器重复约束**：`risk_guard` 中的权重上限与 Phase_6 凸优化器中的 `upper_bounds` 功能高度重合，但两者计算口径可能存在细微差异（前者除 `NAV`，后者除 `individual_account_equity`），导致回测中的实际持仓上限与理论优化结果不一致。
- **卖出函数未纳入 `impairment_factor`**：在 `_sell_asset_action` 中，卖出价格直接使用 `price` 计算，未考虑已计提的减值因子。若资产已减值，卖出时应当用 `price * impairment_factor` 作为估值基准，否则会计入虚增的现金，造成账目微小偏差（对账可能捕捉到）。

## 整体评价与改进方向

### 系统优势
- **实盘级别的交易仿真**：整手截断、平方根冲击、先卖后买、税费扣减、停牌减值、退市清算等细节完备，回测结果具有高度可信度。
- **会计精度极高**：通过 `process_state_6_reconciliation` 强制借贷平衡，任何计算误差都会被立即捕获，体现了量化回测的最高诚信标准。
- **架构防御性极强**：时区自适应、列名嗅探、多级降级（价格穿透、ADV 降级）等设计使引擎在数据不完美时仍可稳健运行。
- **状态机语义明确**：虽然未用枚举类实现，但 `process_state_4/5/6` 的分阶段执行清晰对应了订单生命周期，便于调试和插桩。

### 当前痛点
- **冲击参数化失效**：`config.py` 中定义的冲击系数未被 `execution_fsm` 引用，硬编码值使调参和敏感性分析变得困难。
- **共形预测区间未真正集成**：Phase_6 的区间占位数据（0.02）导致违规检测失去统计意义，这是从 Phase_6 到 Phase_7 的数据契约断裂。
- **流动性约束双重实现且口径不一**：`risk_guard` 和凸优化器的 `upper_bounds` 分别计算，若 NAV 与 `individual_account_equity` 不同步（如回测中 NAV 变化），两者将产生冲突，导致优化目标与实际执行脱节。
- **卖出的减值会计处理不完整**：`_sell_asset_action` 未将减值因子作用于卖出价格，存在会计漏洞。

### 未来演进
- **统一冲击参数**：将 `execution_fsm` 中的硬编码冲击替换为 `config.get('kapha_impact')` 和 `config.get('alpha_impact')`，并支持基于资产特性的动态冲击函数（如流动性分层）。
- **修复共形区间传递**：要求 Phase_6 输出真实的 `q_low`/`q_high` 面板（非占位常量），或让 Phase_7 在区间缺失时自动跳过检测并记录警告，而非徒劳运行。
- **统一流动性约束**：将 `risk_guard` 中的 `compute_individual_position_limit` 逻辑与凸优化器的 `_compute_individual_shares_upper` 合并为单一 PIT 查询函数，并确保 `NAV` 与优化器的账户权益参数一致。
- **完善 FSM 状态枚举**：引入 `OrderStatus` 枚举类（`PENDING -> SUBMITTED -> PARTIAL_FILLED -> FILLED / CANCELED`），显式管理订单状态流转，为高频交易仿真预留扩展接口。
- **引入逐笔成交模拟**：目前为日频批量撮合，未来可扩展至分钟级或 tick 级的事件驱动，以捕捉日内价格波动。

---

## 结语

Phase_7 是 Quant‑4 系统中回测仿真的最高层，它以近乎偏执的会计严谨性（1 元对账红线）和丰富的市场微观结构细节，为策略提供了接近实盘的验证环境。尽管存在冲击参数硬编码和共形区间占位数据等结构性缺陷，但其架构思想——尤其是时区自适应、列名嗅探和强对账机制——为工业级回测引擎的构建提供了极佳的参考。修复上述数据契约断裂和参数化失效问题后，Phase_7 将成为一套足以支撑实盘决策的高置信度仿真平台。
