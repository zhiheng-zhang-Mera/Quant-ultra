# Phase_1_Data_Foundation：底层数据基建深度解析

## 概述

Phase_1（Data Foundation）是 Quant‑4 系统的**数据清洗与底座构建层**，负责将原始行情、财务数据转化为可靠的面板（Panel）数据结构，并彻底消除生存者偏差（Survivorship Bias）。该阶段通过流动性初筛、全收益与退市残值计算、交易状态映射三个子步骤，最终产出跨资产的生存状态矩阵（`alive_mask`），为后续所有量化计算提供坚实、无偏的时空基准。

Phase_1 的设计高度体现工业化量化系统的严苛要求：防御性编程、多源数据降级、自适应资源控制、缓存与断点续传，并与主框架的 `data_bus`、`data_manager`、`audit_logger` 深度集成，是系统鲁棒性的第一道防线。

---

## 模块总览与协作关系

| 文件 | 核心职责 | 依赖关系 |
|------|----------|----------|
| `__init__.py` | 暴露 `execute` 入口，供主引擎调度 | 被 `main_engine.py` 调用 |
| `config.py` | 定义 Phase_1 本地配置阈值（流动性、并发、容量参数） | 被所有子模块引用 |
| `concurrency.py` | 自适应并发限制器（基于 CPU 利用率和错误率动态调整线程数） | 被 `step1_1_screening.py` 使用 |
| `step1_1_screening.py` | 多资产流动性初筛（ADV 计算），容量估算，并缓存结果 | 依赖 `data_bus`、`data_manager`、`concurrency` |
| `step1_2_returns.py` | 计算总收益价格、对数收益率、退市残值，整合退市股票 | 依赖 `data_bus`、`data_manager`、`audit_logger` |
| `step1_3_trading_status.py` | 标记 ST、涨跌停板、上市天数等交易状态约束 | 依赖 `data_bus`、`data_manager` |
| `step1_data_foundation.py` | 串联上述三个步骤，构建 `alive_mask` 生存矩阵并输出最终上下文 | 聚合上述所有子模块 |

## 各模块详解

### 1. `config.py` —— 本地阈值锚点

**功能**  
定义 Phase_1 专用的常量配置，包括：
- 数据起始日期 `START_DATE: "2015-01-01"`（长周期大本营）
- 流动性门槛 `MIN_ADV_THRESHOLD: 1e7`（1000 万元）
- 次新股过滤 `IPO_SAFETY_DAYS: 20` 天
- 容量估算参数 `MAX_PARTICIPATION_RATE`、`EXPECTED_TURNOVER`、`MAX_SINGLE_STOCK_WEIGHT`
- 并发控制参数（自适应上下限、CPU 目标、检查间隔、错误率阈值）
- 缓存过期天数 `CACHE_EXPIRE_DAYS: 7`

**设计亮点**  
- 集中管理所有业务阈值，便于调优和版本控制。
- 并发参数与业务参数分离，清晰反映不同维度的控制策略。

**潜在缺陷**  
- 所有参数硬编码于 Python 文件，未从外部 YAML 配置读取（主引擎已支持 `default_param.yaml`，但 Phase_1 未使用），降低了灵活性和 A/B 测试的便利性。
- `START_DATE` 硬编码为 `2015-01-01`，与主引擎动态计算的起始年份可能不一致，导致数据范围割裂。

---

### 2. `concurrency.py` —— 自适应并发限制器

**功能**  
- 实时监控 CPU 利用率和任务错误率，动态调整 `ThreadPoolExecutor` 的并发工作线程数。
- 当错误率超过阈值（8%）时主动降低并发数，防止远端数据源（如 yfinance）封禁 IP。
- 若 `psutil` 未安装，则降级为静态线程池（使用 `DOWNLOAD_WORKERS` 配置）。

**设计哲学**  
- 典型的“智能反压”机制，将系统负载和外部响应作为反馈信号，实现弹性伸缩。
- 日志双语言输出（英文 + 中文），便于跨国团队理解。
- 线程安全：使用 `Condition` 和锁保护共享状态。

**优点**  
- 极大提升大规模数据拉取的稳定性和成功率，避免因过度并发触发防火墙 RST 硬拦截。
- 错误率感知能快速应对数据源异常，比如因限流导致的失败率飙升。

**客观缺陷**  
- 监控线程每 2 秒采样一次，但 `cpu_percent(interval=0.5)` 可能引入额外开销，在低延时要求下需权衡。
- 错误率统计为全局累计，未按资产或时间窗口滑动，可能导致旧错误持续影响并发度。
- 若 `psutil` 缺失，则完全丧失自适应能力，仅依赖固定线程数，而 `DOWNLOAD_WORKERS` 在配置中设为 4，较保守，可能拖慢速度。

---

### 3. `step1_1_screening.py` —— 流动性筛选与容量估算

**功能**  
- 从 `data_bus.get_universe()` 获取全市场标的，过滤出 A 股（数字代码）及美股（`.US` 后缀）。
- 对每个标的加载近 400 天历史数据，计算平均日成交额（ADV），并记录上市日期、板块类型。
- 根据 `MIN_ADV_THRESHOLD` 和 `IPO_SAFETY_DAYS` 进行过滤，形成初步存活资产池。
- **容量前置估算**：基于 ADV、市场参与率、换手率、单票权重上限，反推理论管理规模上限（`theoretical_aum_limit_base`），并输出容量分布统计。
- 使用 `AdaptiveConcurrencyLimiter` 控制并行度，实现安全高效扫描。
- 结果缓存至 `Data_Cache/screening_results.parquet`，若缓存日期与最新交易日一致则直接加载。

**设计亮点**  
- 双市场适配：区分 A 股主板/科创板/创业板和美股，分别处理涨跌幅和规则差异。
- 容量估算采用“最窄瓶颈”法（取所有股票容量最小值乘以资产数再乘 0.15 保险系数），为资管规模提供保守上限。
- 缓存策略高效：仅在最新交易日变化时重算，极大加速重复运行。

**客观缺陷**  
- `_worker_core` 中通过 `data_bus.load_asset_history` 加载数据，但该方法内部可能未正确处理退市股票（历史数据截止到退市日），导致无法获取退市后的价格信息，影响后续生存者偏差修复。
- `_infer_board_type` 仅根据代码前缀判断，对于美股统一归类为“美股成分股”，缺乏区分（如纳斯达克、纽交所），可能影响涨跌幅规则。
- 容量估算公式 `capacities = (adv * max_part_rate) / (expected_turnover * max_single_weight)` 未考虑协方差或行业集中度，过于简化。
- 缓存仅依赖 `cache_date` 与最新交易日比较，未考虑配置参数变化（如修改阈值后仍使用旧缓存），可能导致结果不一致。

### 4. `step1_2_returns.py` —— 全收益与退市残值计算

**功能**  
- 从 `akshare` 获取已退市 A 股列表，将其加入资产池（与当前筛选出的活跃资产合并），以修复生存者偏差。
- 对每个资产（包括退市股）加载历史行情，提取 `close` 和 `log_return`，并查询 `delisting_residual`（退市残值），若缺失则记录审计事件并默认为 0。
- 将价格、对数收益、残值写入 `data_bus` 的原子存储中，同时缓存到 `total_return_prices.parquet` 以便后续快速恢复。

**设计亮点**  
- **强制纳入退市股**：从根源上避免了经典生存者偏差（Flaw A-8），确保回测中能反映真实的历史可交易标的。
- 缓存设计：若缓存中存在且覆盖最新交易日，且包含所有当前资产，则直接热注入 `data_bus`，跳过繁重计算。
- 审计日志：当退市残值缺失时记录 `DATA_MISSING_DEFAULT_RESIDUAL` 事件，便于追踪数据质量。

**客观缺陷**  
- 退市列表获取仅依赖 `akshare.stock_zh_a_delisted`，若该接口变动或不可用，则无法获取退市股票，退化为仅处理活跃股，丧失纠偏功能。
- 缓存判断条件 `set(assets).issubset(cached_symbols)` 要求当前资产必须是缓存子集，但缓存可能包含更多退市股，这导致若新增退市股不在缓存中，仍会触发重算，但重算后会将所有退市股写入，下次再运行即可命中。这是合理的，但未考虑部分资产因数据拉取失败而缺失的情况。
- `log_return` 依赖 `load_asset_history` 返回的 DataFrame 中直接含有该列，若数据源未提供则直接跳过，未尝试自行计算。
- 残值查询 `data_bus.query_by_pit(sym, dt, "delisting_residual")` 依赖 `data_bus` 的 `append_atom` 预填充，但此处是先查询后写入，顺序正确，但若之前未填充过，则每次都会查询失败并默认 0，造成大量审计日志，且未利用 `query_by_pit` 的缓存能力。

### 5. `step1_3_trading_status.py` —— 交易状态映射

**功能**  
- 获取最新的 ST 股票列表（从 akshare 或 baostock 轮询），作为风险标记。
- 对每个资产确定板块、上市天数，并计算涨跌停价格（基于前一日收盘价）。
- 将状态映射（包括 `is_st`、`limit_up`、`limit_down`、`prev_close` 等）写入 `data_bus` 并缓存至 `trading_status.parquet`。
- 支持多数据源降级，优先 akshare，次选 baostock。

**设计亮点**  
- 多源冗余保证 ST 列表的高可用性。
- 涨跌停规则区分美股（50% 无限制）和 A 股不同板块（ST 5%、科创/创业板 20%、主板 10%），符合监管现实。
- 缓存恢复逻辑与 `step1_1` 类似，仅当最新交易日一致时才复用。

**客观缺陷**  
- ST 列表获取仅执行一次，未按时间点（PIT）进行历史回测，即对于历史回测日期，应使用当时的 ST 状态，而非最新状态。当前实现使用 `now` 时间获取最新 ST 列表，并应用于所有历史日期，这严重违反 PIT 原则，会导致未来信息泄露（例如某股在 2020 年被 ST，但在 2019 年回测时被误标为 ST，影响交易决策）。
- 涨跌停价格基于前一日的 `total_return_price`，但该价格从 `data_bus.query_by_pit` 获取，若该日期无数据（节假日），会使用 `prev_price = 100.0` 的默认值，导致计算错误。
- 未处理停牌状态，仅依赖涨跌停边界，实际交易中停牌无法买卖，此处未做标记，可能高估可交易性。

---

### 6. `step1_data_foundation.py` —— 底座编排器

**功能**  
- 按顺序调用上述三个子步骤。
- **核心产出**：构建 `alive_mask` 矩阵 —— 一个布尔型 DataFrame，行索引为交易日（A 股日历），列为所有资产，元素指示该资产在该日是否“存活”（即已上市且未退市）。
- 同时产出 `adv_data`（模拟的 ADV 面板，目前全为常量 2e7）和 `theoretical_aum_limit`。
- 记录执行耗时和进度日志。

**设计亮点**  
- 通过 `alive_mask` 为下游阶段（如标签计算、特征工程、回测）提供了严格的时间点生存状态，彻底杜绝前瞻性偏差。
- 进度日志细粒度（每 100 个资产打印一次），便于监控大规模资产集的运行进度。

**客观缺陷**  
- **性能严重瓶颈**：构建 `alive_mask` 时，采用双重循环（遍历所有日期 × 所有资产），每个资产调用 `data_manager.fetch_historical` 获取整个历史区间，再逐日判断。这会导致：
  - 重复拉取数据（每个资产至少拉一次，且未复用已拉取数据）。
  - 时间复杂度 O(days * assets)，当资产数 > 5000、交易日 > 3000 时，计算量达千万级，且 Python 循环极慢。
  - 实际上，`asset_bounds` 完全可以从前面的 `step1_1` 和 `step1_2` 中已知的 `hist_df` 获取（它们已经加载了历史数据），但此处又重新拉取，造成巨大的浪费。
- `adv_data` 被赋值为全常量 DataFrame，完全失去了真实的流动性信息，后续容量优化和仓位管理将无法基于实际 ADV，仅依赖初始容量估算（`theoretical_aum_limit`）可能不够精细。
- `alive_mask` 仅依赖上市日期和退市日期，但未考虑停牌、涨跌停等短期不可交易状态，因此其“存活”定义过于宽泛，不是真正的“可交易”状态。

## 整体评价与改进方向

### 系统优势
- **生存者偏差修正**：明确纳入退市股票，体现了量化回测的最高诚信标准。
- **工业化健壮性**：多源数据降级、自适应并发、缓存机制、审计日志，使系统能在大规模生产环境中稳定运行。
- **跨市场支持**：同时处理 A 股和美股，规则差异（涨跌幅、ST）得到细致区分。
- **容量估算前置**：在数据基建阶段就评估策略容量，为组合优化提供早期参考。

### 当前痛点
- **性能冗余**：`alive_mask` 构建重复拉取数据，且双重循环低效，应重构为基于已有历史数据直接派生边界，并使用向量化操作（如 `pd.DataFrame` 的 `apply` 或 `numpy` 广播）。
- **PIT 违反**：`step1_3` 中使用当前日期获取 ST 列表并应用于整个回测区间，严重违背 PIT 原则，必须改为按交易日查询历史 ST 状态（可依赖 `data_bus` 的历史快照或从数据源获取历史 ST 列表）。
- **数据定义不精确**：`alive_mask` 未考虑停牌，导致回测可能交易无法执行的标的，需引入停牌信息（可从行情数据的 `status` 字段获取）。
- **配置硬编码**：除 `config.py` 外，日期范围和路径仍与主引擎耦合不紧密，应统一从 YAML 配置加载。
- **缓存一致性风险**：缓存判断仅基于日期，未校验配置参数版本，可能导致参数更新后仍使用旧缓存。

### 未来演进
- **重构 `alive_mask` 生成**：利用 `step1_1` 中每个资产的 `hist_df` 直接生成上市/退市日期，并合并成 `asset_bounds`，避免二次拉取；使用 `numpy` 广播或 `pandas` 的 `isin` 方法生成布尔矩阵。
- **引入历史 ST / 停牌时间表**：从数据源获取每日 ST 列表和停牌记录，在 `step1_3` 中按时间点写入 `data_bus`，确保 PIT 合规。
- **将 ADV 面板真实化**：将 `step1_1` 计算的 ADV 扩展到每日面板（可使用滚动平均），供后续仓位优化使用。
- **配置外部化**：将 `config.py` 中的阈值迁移到主 YAML 配置，实现统一管理。
- **缓存版本化**：在缓存中记录配置哈希，当配置变化时自动失效缓存。

---

## 结语

Phase_1 作为 Quant‑4 系统的数据基石，已实现高标准的生存者偏差修正、多源降级和自适应控制，为后续 Alpha 挖掘和回测仿真提供了可靠的数据基础。然而，其在 PIT 合规性、性能优化和缓存一致性方面仍存在明显短板，亟需在下一迭代中予以解决。理解这些模块的深层设计意图与潜在陷阱，是正确使用和二次开发该系统的关键。通过持续演进，Phase_1 有望成为业界领先的量产级数据清洗底座。
